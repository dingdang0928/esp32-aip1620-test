# T6350 云端校时接口协议

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 文档版本 | V1.0 |
| 适用设备 | T6350 |
| 接口用途 | 云端向设备下发 UTC 时间和设备所在地时区 |
| 数据编码 | UTF-8 JSON，不带 BOM |
| 传输方式 | 与传输通道无关，可承载于 MQTT、BLE 网关或其他可靠通道 |

本文档定义校时业务载荷。具体 MQTT Topic、QoS、鉴权和加密方式由通信协议另行约定。

当前设备不使用 NTP，也不从 App 单独获取时间。设备启动后，在收到一条有效的云端校时消息之前，时间状态无效，时钟显示为 `00:00`，睡眠记录和闹钟等依赖时间的功能不可用。

## 2. 核心约定

云端每次校时必须同时下发以下两项数据：

1. 当前 UTC Unix 时间戳，单位为毫秒。
2. 设备所在地对应的 POSIX TZ 时区字符串。

设备内部始终以 UTC 运行。显示时间时，设备根据 POSIX TZ 将 UTC 转换为当地时间，因此同一个 UTC 时间戳在不同时区会显示不同的本地时间。

> 禁止把当地日历时间直接转换成“伪 UTC 时间戳”发送，否则设备会再次叠加时区偏移，造成时间错误。

## 3. 下行校时消息

### 3.1 JSON 格式

```json
{
  "type": "time_sync",
  "request_id": "ts-20290928-000001",
  "utc_time_ms": 1885253280000,
  "timezone": "CST-8"
}
```

### 3.2 字段定义

| 字段 | 类型 | 必填 | 约束 | 说明 |
| --- | --- | --- | --- | --- |
| `type` | string | 是 | 固定为 `time_sync` | 消息类型，用于设备通信层分发 |
| `request_id` | string | 建议 | 建议不超过 64 字节，同一条请求保持唯一 | 用于日志追踪、应答匹配和问题排查 |
| `utc_time_ms` | integer | 是 | `1704067200000 <= value < 4102444800000` | UTC Unix 时间戳，单位毫秒；对应有效范围为 2024-01-01（含）至 2100-01-01（不含） |
| `timezone` | string | 是 | 1～96 字节，不允许空白字符 | POSIX TZ 字符串，不是 IANA 时区名称 |

`utc_time_ms` 必须作为 JSON 整数发送，不能发送浮点数、秒级时间戳或格式化日期字符串。

正确示例：

```json
"utc_time_ms": 1885253280000
```

错误示例：

```json
"utc_time_ms": 1885253280
```

上面的错误值是秒级时间戳，设备会拒绝。

## 4. POSIX 时区规则

### 4.1 固定时区

POSIX TZ 的偏移符号与常见的 `UTC+8` 写法相反。例如，中国标准时间 UTC+8 应写成 `CST-8`。

| 地区 | UTC 偏移 | `timezone` 示例 |
| --- | ---: | --- |
| UTC | UTC+0 | `UTC0` |
| 中国大陆 | UTC+8 | `CST-8` |
| 日本 | UTC+9 | `JST-9` |
| 印度 | UTC+5:30 | `IST-5:30` |
| 美洲固定 UTC-5（不使用夏令时） | UTC-5 | `EST5` |

`CST`、`JST`、`IST` 等前缀主要用于本地时间的时区缩写，真正决定时间偏移的是后面的数字和规则。云端不能只发送 `CST`。

### 4.2 夏令时地区

有夏令时的地区必须下发包含夏令时起止规则的完整 POSIX TZ 字符串。不能只下发当前 UTC 偏移，否则进入或退出夏令时后设备不会自动调整。

| 地区 | `timezone` 示例 |
| --- | --- |
| 美国东部 | `EST5EDT,M3.2.0/2,M11.1.0/2` |
| 英国 | `GMT0BST,M3.5.0/1,M10.5.0/2` |
| 中欧 | `CET-1CEST,M3.5.0/2,M10.5.0/3` |
| 澳大利亚悉尼 | `AEST-10AEDT,M10.1.0/2,M4.1.0/3` |

夏令时政策可能发生变化。云端应维护地区到 POSIX TZ 的映射，并在每次校时时下发当前有效规则。

### 4.3 不支持的格式

设备当前没有 IANA 时区数据库，因此以下内容不能直接作为 `timezone` 下发：

```text
Asia/Shanghai
America/New_York
Europe/London
UTC+8
GMT+8
```

云端必须先把地区转换成设备可识别的 POSIX TZ 字符串。

## 5. 设备处理流程

设备通信应用层收到消息后，应按以下顺序处理：

1. 解析 JSON，并确认 `type` 为 `time_sync`。
2. 检查 `utc_time_ms` 是否为整数且处于有效范围内。
3. 检查 `timezone` 是否存在、长度是否合法且不包含空白字符。
4. 调用：

   ```c
   Inf_RTC_SyncFromCloud(utc_time_ms, timezone);
   ```

5. 校时成功后立即调用：

   ```c
   App_ClockDisplay_Refresh();
   ```

6. 向云端返回处理结果。

设备成功校时后：

- 系统 UTC 时间立即更新；
- POSIX 时区立即生效；
- 屏幕按照当地时间显示 `HH:MM`；
- 睡眠记录等依赖时间的业务可以正常使用。

## 6. 建议的设备应答

> 本节是通信层建议格式。当前 RTC INF 接口已经具备返回结果，但真实云端通信解析和应答尚待接入。

成功应答：

```json
{
  "type": "time_sync_ack",
  "request_id": "ts-20290928-000001",
  "success": true,
  "code": "OK"
}
```

失败应答：

```json
{
  "type": "time_sync_ack",
  "request_id": "ts-20290928-000001",
  "success": false,
  "code": "INVALID_TIMEZONE"
}
```

建议错误码：

| `code` | 含义 | 云端处理建议 |
| --- | --- | --- |
| `OK` | 校时成功 | 记录设备最后校时时间和时区 |
| `INVALID_PAYLOAD` | JSON 或必要字段错误 | 检查协议实现，不要原样重试 |
| `INVALID_TIMESTAMP` | 时间戳单位或范围错误 | 重新获取当前 UTC 毫秒时间戳 |
| `INVALID_TIMEZONE` | 时区字符串缺失或非法 | 修正地区到 POSIX TZ 的映射 |
| `RTC_NOT_READY` | 设备 RTC 模块尚未初始化 | 延迟后使用新的当前时间重试 |
| `RTC_SET_FAILED` | 设备设置系统时间失败 | 延迟后使用新的当前时间重试并上报告警 |

## 7. 下发时机和重试要求

云端应在以下场景发送校时消息：

- 设备首次绑定并连接云端后；
- 设备每次重新启动并重新上线后；
- 用户修改设备所在地或时区后；
- 地区夏令时规则发生变化后；
- 设备长时间运行时定期校时，建议至少每 24 小时一次；
- 设备明确上报时间无效时。

重试要求：

- 每次发送或重试时，都必须重新生成当时最新的 `utc_time_ms`。
- 不允许缓存并长期重放旧的校时消息，否则设备时间会被调回过去。
- 当前固件允许在有效范围内向前或向后校时，尚未实现通信层防重放策略。
- 建议使用可靠传输、身份认证和加密，避免未授权校时。
- 收到成功应答后停止当前请求的重试。

由于设备在收到消息时直接应用 `utc_time_ms`，传输延迟会直接形成同等大小的时间误差。应尽量使用低延迟链路，并在消息发送前最后一刻生成时间戳。

## 8. 联调测试用例

### 8.1 同一个 UTC 时间在不同地区显示

测试时间：

```text
UTC:     2029-09-28 01:28:00
Unix ms: 1885253280000
```

| `timezone` | 预期当地时间 | 屏幕预期 |
| --- | --- | --- |
| `UTC0` | 2029-09-28 01:28:00 | `01:28` |
| `CST-8` | 2029-09-28 09:28:00 | `09:28` |
| `JST-9` | 2029-09-28 10:28:00 | `10:28` |
| `IST-5:30` | 2029-09-28 06:58:00 | `06:58` |
| `EST5EDT,M3.2.0/2,M11.1.0/2` | 2029-09-27 21:28:00 | `21:28` |
| `GMT0BST,M3.5.0/1,M10.5.0/2` | 2029-09-28 02:28:00 | `02:28` |

### 8.2 美国东部冬季时间

请求：

```json
{
  "type": "time_sync",
  "request_id": "dst-winter-001",
  "utc_time_ms": 1893115680000,
  "timezone": "EST5EDT,M3.2.0/2,M11.1.0/2"
}
```

对应 UTC 时间为 `2029-12-28 01:28:00`，美国东部处于冬季标准时间 UTC-5，预期当地时间为 `2029-12-27 20:28:00`，屏幕显示 `20:28`。

### 8.3 应当拒绝的数据

| 测试输入 | 拒绝原因 |
| --- | --- |
| `utc_time_ms: 1885253280` | 错误地使用了秒级时间戳 |
| `utc_time_ms: 4102444800000` | 已达到设备允许范围的上限 |
| `timezone: ""` | 时区为空 |
| `timezone: "Asia/Shanghai"` | 不是设备约定的 POSIX TZ 格式 |
| 缺少 `utc_time_ms` 或 `timezone` | 必填字段缺失 |

## 9. 当前固件边界

- RTC INF 接口已支持 UTC 毫秒时间戳和 POSIX TZ，并使用互斥锁保护校时与本地时间转换。
- RTC DRI 层只读写系统 UTC 时间，不处理云端协议和时区，层次职责清晰。
- 当前串口测试已经按 `UTC_MS + POSIX_TZ` 方式验证校时。
- 真实云端消息解析、应答和防重放逻辑尚未接入，需要由后续通信应用层实现。
- 当前固件只检查时区字符串的长度和字符安全，不能完整判断 POSIX TZ 规则在语义上是否正确。因此云端必须使用经过测试的时区映射表，不能透传用户自由输入的时区字符串。
